This manual describes the features and customization options for the Emacs Lisp file =org-linear.el=.

* Overview
:PROPERTIES:
:CUSTOM_ID: h:overview
:END:

=org-linear.el= keeps the issues of one or more [[https://linear.app][Linear]] teams in an Org file and syncs the two in both directions. You work on your issues with the Org commands you already use: change a TODO keyword to move an issue through its workflow, set a deadline for its due date, add a note to comment on it, refile it to move it to another project. Changes made in Linear, by you or by your colleagues, reach the file at the next sync.

Linear stays the authoritative copy and the file is a mirror. The package exists because the alternatives each give up half of that: Linear's own interface lives outside Emacs, and a one-way export cannot be edited. Unlike an export, =org-linear= remembers what each issue looked like at the last sync, so it can tell which side changed a field and merge the two without overwriting either.

The package talks to Linear's GraphQL API through =curl= and converts descriptions and comments between Markdown and Org with [[https://pandoc.org][pandoc]]. Both run as subprocesses, so Emacs never waits on the network.

Its capabilities fall into four groups:

- The file: how issues, projects and their fields appear in Org ([[#h:the-file][The file]]).
- Syncing: when a sync runs, how it merges, and what happens on conflicts ([[#h:syncing][Syncing]]).
- Setup: the API key, the teams and the mappings ([[#h:user-options][User options]]).
- The agenda: a single command that lists your open issues, and your deadlines among your other tasks ([[#h:agenda][The agenda]]).

* Installation
:PROPERTIES:
:CUSTOM_ID: h:installation
:END:

=org-linear= requires Emacs 29.1 or later, Org 9.7 or later, and the =curl= and =pandoc= programs on your =exec-path=.

With Elpaca:

#+begin_src emacs-lisp
(use-package org-linear
  :ensure (:host github :repo "benthamite/org-linear")
  :custom
  (org-linear-teams '("ENG"))
  :config
  (org-linear-auto-sync-mode))
#+end_src

With Emacs's built-in =package-vc= (Emacs 30 or later):

#+begin_src emacs-lisp
(use-package org-linear
  :vc (:url "https://github.com/benthamite/org-linear")
  :custom
  (org-linear-teams '("ENG"))
  :config
  (org-linear-auto-sync-mode))
#+end_src

Then create a personal API key in Linear (Settings, Security & access, Personal API keys), give it access to the teams you mirror, and make it available to the package ([[#h:api-key][The API key]]).

* The file
:PROPERTIES:
:CUSTOM_ID: h:the-file
:END:

The file is ~org-linear-file~. When it does not exist, the first sync creates it with ~org-linear-file-header~ and fills it. Each project is a level-1 heading with a =LINEAR_PROJECT= property, and each issue a level-2 heading under its project. Issues without a project go under a heading named "No project".

#+begin_src org
,* Website
:PROPERTIES:
:LINEAR_PROJECT: 3f1c...
:END:
,** DOING [#B] Fix the broken signup form                  :ana:bug:
DEADLINE: <2026-11-12 Thu>
:PROPERTIES:
:LINEAR_ID: ENG-123
:LINEAR_UUID: 6b0e...
:LINEAR_URL: https://linear.app/acme/issue/ENG-123/fix-the-broken-signup-form
:END:
:LOGBOOK:
- Note taken on [2026-11-02 Mon 10:14] (Sam Lee) \\
  I can reproduce it on Safari only.
:END:
The form rejects valid email addresses with a plus sign.
#+end_src

** How fields map
:PROPERTIES:
:CUSTOM_ID: h:field-mapping
:END:

| Linear         | Org                                                          |
|----------------+--------------------------------------------------------------|
| Title          | The heading's title                                          |
| Workflow state | TODO keyword ([[#h:states][Workflow states and keywords]])                   |
| Priority       | Priority cookie (~org-linear-priorities~)                    |
| Assignee       | A tag for the person (~org-linear-user-tags~)                |
| Labels         | Tags                                                         |
| Due date       | =DEADLINE=                                                   |
| Project        | The level-1 heading the issue sits under                     |
| Description    | The heading's body, converted from and to Markdown by pandoc |
| Comments       | Notes in the log drawer                                      |

The identifier, the issue's internal ID and its URL are kept in the =LINEAR_ID=, =LINEAR_UUID= and =LINEAR_URL= properties. The sync maintains them; do not edit them.

Tags that name neither a team member nor a label are yours: the sync leaves them alone and never sends them. A label's tag is its name with every character Org does not allow in tags replaced by =_=, so the label =requested-by:peter= becomes the tag =requested_by_peter=. A tag you add sends the label of that name that the issue's team can use; if several can, it is logged and not sent.

Linear issues have no start date, so by default =SCHEDULED= is not synced: use it freely to defer an issue in your own agenda.

#+vindex: org-linear-start-date-label
A team can stand in for a start date with a =Start: YYYY-MM-DD= first line in the description and a label. Set ~org-linear-start-date-label~ to that label's name, such as ="deferred"=, and =SCHEDULED= syncs both ways with the two of them. A date in the file then shows as =SCHEDULED= alone: the line leaves the body, and the label's tag leaves the tags. Setting, moving or removing =SCHEDULED= rewrites the line and sets or removes the label on Linear, and for an issue in triage it also snoozes the issue until the start of that date in your time zone, or ends the snooze. Nothing is written when you turn the option on, unless a synced heading already has a =SCHEDULED= of its own: that date is sent.

Every =SCHEDULED= on a synced issue is then visible to your team, and the label stays after the date passes, until someone removes the date. A Linear view that hides the label keeps hiding the issue until then.

** Workflow states and keywords
:PROPERTIES:
:CUSTOM_ID: h:states
:END:

Each issue's workflow state becomes a TODO keyword. By default the keyword depends only on the state's type (~org-linear-type-keywords~): triage issues are =TRIAGE=, backlog issues =BACKLOG=, unstarted ones =TODO=, started ones =DOING=, completed ones =DONE=, and canceled or duplicate ones =CANCELLED=. ~org-linear-state-keywords~ gives individual states keywords of their own, for instance a =WAITING= keyword for a state named "Waiting".

When you change a keyword in the file, the sync sends it as the state ~org-linear-keyword-states~ names for it, or else as the first state of the issue's team that maps to that keyword, in Linear's order of state types and positions.

The file's own =#+TODO= line, written from ~org-linear-file-header~ when the file is created, must list every keyword these options can produce. The default header marks =CANCELLED= with =@=, so Org asks for a note when you cancel an issue; the sync posts that note as a comment, which records why the issue was dropped.

** Working with issues
:PROPERTIES:
:CUSTOM_ID: h:working-with-issues
:END:

#+findex: org-linear-set-project
Edit issues with ordinary Org commands, then save the file; with ~org-linear-auto-sync-mode~ the save sends your changes ([[#h:syncing][Syncing]]).

- To comment on an issue, add a note with =C-c C-z= (~org-add-note~), or with =M-x org-linear-comment=, which also works from the list of your issues. Notes attached to state changes, such as the one the default header asks for when you cancel an issue, are posted too, prefixed with the new keyword.
- To create an issue, add a level-2 heading with a TODO keyword under a project heading, with its description as the body. At the next sync it is created in Linear, in the project's team, and gets its =LINEAR_ID=. Until Linear confirms the issue, the heading holds the ID it was sent with as =LINEAR_PENDING_UUID=, so that an issue whose creation was not confirmed is found by the next sync rather than created twice.
- To move an issue to another project, refile it with =C-c C-w=, or run =M-x org-linear-set-project=, which also works from the list of your issues. Either way you choose among the teams' projects only, with "No project" to clear it, and the file is saved, which sends the move. With a prefix argument, =C-c C-w= runs ~org-refile~ as usual, for instance to jump to a heading. Without milestones and sub-issues ([[#h:mirror-hierarchy][Milestones and sub-issues]]), an issue has to stay a level-2 heading: refiled by other means under another issue, it drops out of the sync, which adds it back as a second heading.
- To assign an issue, tag it with the person's tag; an issue has one assignee, so a heading with two people's tags sends no assignee and the sync log says why.

Deleting a heading does not delete the issue: it comes back at the next sync, with its description and comments. To drop an issue, cancel it.

An issue deleted in Linear leaves the file at the next sync. If its heading holds edits, notes or subheadings not in Linear, which can no longer take them, it moves with them to the archive file (see [[#h:closed-issues][Closed issues]]) and the sync log says so; with no archive file it stays in the file.

#+findex: org-linear-browse
=M-x org-linear-browse= browses the issue at point in Linear, in the file or the list of your issues.

#+findex: org-linear-visit
=M-x org-linear-visit= visits ~org-linear-file~.

** Milestones and sub-issues
:PROPERTIES:
:CUSTOM_ID: h:mirror-hierarchy
:END:

#+vindex: org-linear-milestone-keywords
Set ~org-linear-milestone-keywords~, for instance to ~("MILESTONE")~, and the file also shows each project's milestones and the issues' parents. Add the keyword to the file's =#+TODO= line. Linear stays the primary copy: these relations merge as the other fields do, and when both sides changed one, Linear's value wins and yours goes to the sync log.

- Each milestone of a project is a level-2 heading under the project's heading, with the first of those keywords, its name as title, its target date as =DEADLINE= and its description as body. Its ID is in =LINEAR_MILESTONE=. The keyword stands for no status; Linear works that out itself.
- An issue in a milestone sits under the milestone's heading; the project's other issues come before its milestones.
- A sub-issue sits under its parent's heading when the two share project and milestone. Otherwise it sits where its own project and milestone put it, and its =LINEAR_PARENT= property holds its parent's ID.

#+begin_src org
,* Website
,** TODO Pick a domain
,*** TODO Compare registrars                 sub-issue of Pick a domain
,** MILESTONE Launch
DEADLINE: <2026-12-01 Tue>
,*** TODO Write the copy                     issue in the milestone Launch
#+end_src

Moving headings sends their relations. Move an issue under a milestone heading and it joins that milestone; under another issue and it becomes that issue's sub-issue, in that issue's project and milestone; back to its project's level and it leaves its parent and milestone. Delete =LINEAR_PARENT= to detach a sub-issue that sits apart from its parent. A new milestone heading under a project heading becomes a milestone of that project, and a new TODO heading under an issue or milestone becomes an issue there; an issue moved under a milestone that is not yet in Linear joins it in the sync that runs once it is. Only what you moved is sent: when Linear moves a parent to another project, its sub-issues stay in theirs, out from under it.

A milestone deleted in Linear leaves the file, and its issues move to the project's level, as Linear takes them out of it. If its heading holds edits or subheadings not in Linear, it stays as a plain heading, without keyword or ID. Deleting a milestone's heading deletes nothing in Linear: it comes back at the next sync. When a parent leaves the file, its open sub-issues stay, each with its parent in =LINEAR_PARENT=. ~org-linear-archive~ does not archive an issue that still holds sub-issues.

** Closed issues
:PROPERTIES:
:CUSTOM_ID: h:closed-issues
:END:

The file holds every open issue of the teams and the issues closed in the last ~org-linear-closed-retention-days~ days. Older closed issues leave the file at the next sync, unless their heading holds unsent edits or notes; such a heading stays, keeps syncing its edits, and leaves once it has nothing unsent.

#+vindex: org-linear-archive-file
An issue that leaves moves to the archive file named by ~org-linear-archive-file~, under a heading named after its project, with the properties Org's archiving adds (=ARCHIVE_TIME=, =ARCHIVE_OLPATH= and the like). Your subheadings and notes go with it. By default the archive is =linear-archive.org= next to =linear.org=: a =%s= in the option stands for the name of ~org-linear-file~ without its directory and extension, and a relative name is relative to that file's directory. The sync creates the archive with the file's =#+TODO= and =#+PRIORITIES= lines and saves it before the file. While the archive's buffer has unsaved edits, or the archive changed on disk, closed issues stay in the file and the sync log says why; they move at the first sync after you save or revert it. Neither the kill ring nor the clipboard is touched.

#+findex: org-linear-archive-closed
#+findex: org-linear-archive
You need not wait for the retention period to end. =M-x org-linear-archive-closed= archives every closed issue in the file at once, and =M-x org-linear-archive= the one at point; in the file, under ~org-linear-auto-sync-mode~, it replaces ~org-archive-subtree~ (=C-c C-x C-s=), which it calls for a heading that is not an issue. Either way the sync remembers the issue and leaves it out of the file while it stays closed; if someone reopens it in Linear, it comes back. Neither archives an open issue, which the next sync would bring back, nor one whose heading holds edits or notes not yet in Linear: sync first. They save the archive and the sync state, and the file too unless it had unsaved edits of yours.

Set ~org-linear-archive-file~ to =nil= to delete closed issues instead. A heading with subheadings of your own then stays in the file for good, and the sync log says so.

* Syncing
:PROPERTIES:
:CUSTOM_ID: h:syncing
:END:

#+findex: org-linear-sync
=M-x org-linear-sync= saves the file, fetches the teams' issues, merges them with the file and sends the file's changes to Linear. It returns at once; the work runs in the background and a message reports when it starts and how it ended. A background sync reports only changes, so it stays out of your echo area. The first sync converts every description and comment, so it can take a few minutes; later ones convert only what changed.

The merge is three-way. For each field the sync compares the file and Linear with the issue as it was at the last sync, kept in ~org-linear-state-file~:

- A field changed only in Linear is updated in the file.
- A field changed only in the file is sent to Linear.
- When both sides changed a field, Linear's value wins, and yours is recorded in the sync log.

Before each write the sync checks when the issue was last edited. If someone changed it in Linear after the sync read it, the write is refused and the issue is merged again at the next sync, so a change made in Linear is never overwritten. A write Linear rejects, for instance for an invalid value, is logged and not retried until you change what was sent; the sync's other writes still go through. A write that fails before Linear judges it, through a timeout, a server error or a rate limit, ends the sync instead, and the next sync tries it again.

A sync never changes the file while it has unsaved edits, and never applies changes if the file changed on disk since you visited it. It reads the file in slices of a few hundredths of a second, between which Emacs handles your input, and then applies Linear's changes at once, so that the time Emacs waits grows with the number of changes, not the size of the file. If you edit the file while it reads, nothing is applied, the sync log says so, and the next sync starts afresh. The changes a sync makes clear the buffer's undo history, since undoing them would send a reversal of your colleagues' changes to Linear.

#+findex: org-linear-auto-sync-mode
#+findex: org-linear-file-mode
~org-linear-auto-sync-mode~ is a global minor mode that syncs whenever you save or visit the file, and every ~org-linear-pull-interval~ seconds while the file has no unsaved edits. In the file's buffer it turns on ~org-linear-file-mode~, which runs a sync after each save.

#+findex: org-linear-show-log
=M-x org-linear-show-log= shows the sync log: conflicts, refused and rejected writes, issues not created, and errors. When a sync fails, its message points there.

* The agenda
:PROPERTIES:
:CUSTOM_ID: h:agenda
:END:

#+findex: org-linear-my-issues
#+vindex: org-linear-my-issues-sections
The file holds every open issue of the teams, so it is not the place to see what is yours. =M-x org-linear-my-issues= is: it opens an agenda of your open issues, with each one's project (in a column as wide as the longest project name) and due month and day, grouped into the sections of ~org-linear-my-issues-sections~. By default those are triage, in progress, waiting and to do; a section whose keyword the file does not define is left out, and backlog issues are not shown. A due date that is today or past is shown in ~org-imminent-deadline~, and one within ~org-deadline-warning-days~ in ~org-upcoming-deadline~. Each call rebuilds the list, even with ~org-agenda-sticky~ on. From the list, =t= changes an issue's status and rebuilds the list, so the issue moves to its new section and point lands on the next one. =C-c C-w=, or any key on ~org-agenda-refile~, moves an issue to another project (~org-linear-set-project~). =.= opens ~org-linear-menu~ (in place of the agenda's jump to today, which a list of issues has no use for), =TAB= shows an issue's heading in another window, =C-x C-s= saves the file, which sends your changes to Linear, and =g= refreshes the list. Issues scheduled for a later day stay out of it until that day; every other issue is shown, whatever your ~org-agenda-todo-ignore-*~ options say. Killing the buffer of the file also kills the list, whose lines would otherwise lead nowhere.

#+vindex: org-linear-my-issues-sync
The list opens at once from the file and then syncs, unless the file has unsaved edits, and it is rebuilt with point on the same issue if the sync brings changes. Set ~org-linear-my-issues-sync~ to =nil= to turn this off.

Add ~org-linear-file~ to ~org-agenda-files~ to see your issues' deadlines with the rest of your tasks.

#+findex: org-linear-agenda-skip
#+vindex: org-linear-hide-others-in-agenda
#+vindex: org-linear-agenda-keep-tags
~org-linear-agenda-skip~ hides issues assigned to someone else. Set it as ~org-agenda-skip-function-global~ to apply it to every agenda view; issues with no assignee and issues assigned to you stay. So do issues with a tag in ~org-linear-agenda-keep-tags~, =nil= by default, which suits a team that labels work it shares, for instance with =joint=. ~org-linear-hide-others-in-agenda~, =t= by default, turns the filter off without removing it.

#+begin_src emacs-lisp
(setq org-agenda-skip-function-global #'org-linear-agenda-skip)
#+end_src

* Transient menu
:PROPERTIES:
:CUSTOM_ID: h:transient-menu
:END:

#+findex: org-linear-menu
=M-x org-linear-menu= gathers the package's commands in a transient menu. In the list of your issues, =.= opens it; elsewhere the package binds it to no key, so bind it yourself if you use it often.

| Key | Command                     | What it does                                 |
|-----+-----------------------------+----------------------------------------------|
| =m= | ~org-linear-my-issues~      | Show your open issues                        |
| =v= | ~org-linear-visit~          | Visit the file                               |
| =b= | ~org-linear-browse~         | Browse the issue at point in Linear          |
| =t= | ~org-linear-my-issues-todo~ | Change the status of the issue at point      |
| =c= | ~org-linear-comment~        | Comment on the issue at point                |
| =p= | ~org-linear-set-project~    | Move the issue at point to another project   |
| =x= | ~org-linear-archive~        | Archive the closed issue at point            |
| =X= | ~org-linear-archive-closed~ | Archive every closed issue now               |
| =s= | ~org-linear-sync~           | Sync now                                     |
| =a= | ~org-linear-auto-sync-mode~ | Turn syncing on save, visit and timer on/off |
| =l= | ~org-linear-show-log~       | Show the sync log                            |

Every key is always shown; =b=, =t=, =c= and =p= act on the issue at point, in the file or in the list of your issues. The =a= key shows whether the mode is on, and the menu stays open after you press it.

* User options
:PROPERTIES:
:CUSTOM_ID: h:user-options
:END:

** Teams and file
:PROPERTIES:
:CUSTOM_ID: h:teams-and-file
:END:

#+vindex: org-linear-teams
The user option ~org-linear-teams~ lists the keys of the teams whose issues the file mirrors, such as ="ENG"=. It is =nil= by default, and a sync refuses to run until you set it.

#+vindex: org-linear-file
~org-linear-file~ is the mirrored Org file, by default =linear.org= in ~org-directory~.

#+vindex: org-linear-file-header
~org-linear-file-header~ is the text a new file starts with. Its =#+TODO= line must cover the keywords of [[#h:states][Workflow states and keywords]], and its =#+PRIORITIES= line the cookies of ~org-linear-priorities~. Notes must go into a drawer, or they would count as part of the description: the default header's =logdrawer= startup option sees to that, and you may drop it if your ~org-log-into-drawer~ is already set. Change the header before the first sync; afterwards, edit the file's header directly.

#+vindex: org-linear-state-file
~org-linear-state-file~ holds each issue as it was at the last sync, by default =org-linear/state.eld= under =$XDG_STATE_HOME= or =~/.local/state=. Deleting it makes the next sync treat Linear's values as the starting point. The sync replaces it whole on each write, so a write cut short, by a crash or a full disk, leaves the previous state intact.

#+vindex: org-linear-closed-retention-days
~org-linear-closed-retention-days~, 7 by default, is how many days a closed issue stays in the file before it moves to the archive ([[#h:closed-issues][Closed issues]]). With 0 it does not stay: it leaves at the first sync that finds it closed, and an issue you close in the file leaves right after the sync that sends the change.

#+vindex: org-linear-pull-interval
~org-linear-pull-interval~, 600 by default, is the number of seconds between background syncs in ~org-linear-auto-sync-mode~.

** The API key
:PROPERTIES:
:CUSTOM_ID: h:api-key
:END:

The sync reads your Linear API key at the start of each sync and forgets it at the end.

#+vindex: org-linear-api-key-command
~org-linear-api-key-command~, a command as a list of strings, prints the key. It runs asynchronously, so it suits a password manager's command line. It takes precedence over the next option.

#+vindex: org-linear-api-key
~org-linear-api-key~ is the key itself or a function that returns it. When it is =nil=, the default, the key is read with =auth-source= for the host =api.linear.app=, for instance from a line in =~/.authinfo.gpg=:

#+begin_example
machine api.linear.app password lin_api_YOURKEY
#+end_example

#+vindex: org-linear-api-key-forget-command
If your command caches the key, set ~org-linear-api-key-forget-command~ to a command that drops the cached copy. When Linear rejects the key, the sync runs it and retries once, so a rotated key is read afresh.

The key reaches =curl= on its standard input, never on its command line, where other processes could see it.

** Mappings
:PROPERTIES:
:CUSTOM_ID: h:mapping-options
:END:

#+vindex: org-linear-type-keywords
#+vindex: org-linear-state-keywords
#+vindex: org-linear-keyword-states
~org-linear-type-keywords~ maps state types to keywords, ~org-linear-state-keywords~ maps individual state names to keywords, and ~org-linear-keyword-states~ chooses which state a keyword is sent as ([[#h:states][Workflow states and keywords]]). For example, a team with a "Waiting" state and a "Rejected" state might use:

#+begin_src emacs-lisp
(setq org-linear-state-keywords '(("Waiting" . "WAITING"))
      org-linear-keyword-states '(("CANCELLED" . "Rejected")))
#+end_src

#+vindex: org-linear-priorities
~org-linear-priorities~ maps Linear's priorities, 1 (urgent) to 4 (low), to Org cookies; it is =A= to =D= by default. Linear's "no priority" is no cookie. A cookie not listed is sent as the priority of the nearest listed cookie above it, so with numeric priorities you can map only some numbers:

#+begin_src emacs-lisp
(setq org-linear-priorities '((1 . "1") (2 . "2") (3 . "4") (4 . "6")))
#+end_src

#+vindex: org-linear-user-tags
~org-linear-user-tags~ maps team members' names to tags. A member not listed gets the first word of their name in lower case, or their full name, as in "peter_hartree", when another member would get the same tag, so that a tag always stands for one person. Members of other teams have no tag; an issue assigned to one of them keeps that assignee, since the file cannot represent it.

** Programs
:PROPERTIES:
:CUSTOM_ID: h:programs
:END:

#+vindex: org-linear-curl-program
#+vindex: org-linear-pandoc-program
#+vindex: org-linear-timeout
~org-linear-curl-program~ and ~org-linear-pandoc-program~ name the =curl= and =pandoc= executables. ~org-linear-timeout~, 60 by default, is how many seconds a request to Linear may take before it is abandoned and the sync fails.

** Profiles
:PROPERTIES:
:CUSTOM_ID: h:profiles
:END:

#+vindex: org-linear-profiles
The options above make up the default profile. ~org-linear-profiles~ adds further ones, each with its own options, sync state, log and timer, so that one Emacs can sync with several Linear workspaces. It is an alist of =(NAME . OPTIONS)=: NAME is a symbol and OPTIONS a plist whose keys are option names without the =org-linear-= prefix. An option a profile leaves out takes its global value, except ~org-linear-state-file~, which defaults to a file named after the profile beside the global one. For example:

#+begin_src emacs-lisp
(setq org-linear-profiles
      '((personal :teams ("ME")
                  :file "~/org/personal-linear.org"
                  :api-key-command ("my-password-tool" "read" "linear-personal"))))
#+end_src

The default profile syncs when ~org-linear-teams~ is set; the others always do under ~org-linear-auto-sync-mode~. =M-x org-linear-sync= syncs the profile of the current buffer; with a prefix argument it asks which. ~org-linear-show-log~ shows the current buffer's profile's log, =*org-linear: NAME*= for a named profile. A sync that fails ends with the error in its own profile's log, and the other profiles keep syncing.

* The in-place layout
:PROPERTIES:
:CUSTOM_ID: h:in-place
:END:

#+vindex: org-linear-layout
By default org-linear mirrors Linear into one file, with Linear as the primary copy. Setting ~org-linear-layout~ to =in-place=, usually in a profile of its own ([[#h:profiles][Profiles]]), syncs TODO headings wherever they already are, across many files, with Org as the primary copy. A heading is linked to its issue by its =LINEAR_UUID= property.

#+vindex: org-linear-directories
#+vindex: org-linear-exclude-files
#+vindex: org-linear-exclude-tags
#+vindex: org-linear-exclude-keywords
The headings synced are the open TODO headings in the =.org= files under ~org-linear-directories~, searched recursively, except those in files matching a regexp of ~org-linear-exclude-files~, those with a tag in ~org-linear-exclude-tags~ (inherited tags count), those with a keyword in ~org-linear-exclude-keywords~, and habits. Exclusions apply to linked headings too: a linked heading that becomes excluded stops syncing, and its issue is left as it is. A linked heading you close in Org still sends its closing.

What a sync does:

- It reads only the files that changed since the last sync or still hold headings to create, and fetches only the issues that changed in Linear since then. The first sync reads every file and opens those with TODO headings, which can take some seconds, so background syncs never make it: start it with =M-x org-linear-sync=. Finding which files changed looks each file up in a table of open buffers built once per sync. A sync reads the files, and later applies Linear's changes to them, in slices of a few hundredths of a second, between which Emacs handles your input, so that even a sync that reads every file, as the first one does or one after you change an option that decides the scope, does not hold Emacs up; such a sync takes longer to finish instead.
- A new heading in scope gets an issue. Before anything is sent, the heading gets the issue's ID as =LINEAR_PENDING_UUID= and its file is saved, so an answer lost on the way back is found by the next sync rather than repeated, and a creation that failed before Linear acted on it is sent again. Once Linear confirms them, the new issues' IDs are written into their headings and each file is saved once, at the end of the sync. At most ~org-linear-create-limit~ issues are created per sync, and the rest wait for the next scheduled sync rather than an immediate one, so a first import spreads over several and keeps within Linear's hourly request limit. Each issue gets a label =file:NAME= naming the file its heading is in, created in Linear when missing.
- Changes on either side are merged field by field, as in the mirror layout. When a field changed on both sides, ~org-linear-conflict-winner~ decides: set it to =org= for this layout, and Linear's value goes to the sync log.
- An issue created in Linear goes under the heading ~org-linear-inbox-heading~ of ~org-linear-inbox-file~. Refile it anywhere in scope and it keeps syncing.
- An issue closed in Linear sets its heading's done keyword; the heading stays. A heading with a repeater repeats instead, once for each time the issue was closed: the =LINEAR_REPEATED= property records the closing it acted on.
- An issue deleted in Linear cancels its heading, which keeps its text and loses its link, so it is not created again.
- A linked heading that is no longer in any file under ~org-linear-directories~ (deleted, or moved out) archives its issue in Linear. A heading moved to an =_archive= file still counts as present. If more than ~org-linear-archive-limit~ issues would be archived at once, as when a directory leaves the option, none is, and the log says why. An issue Linear no longer has is forgotten instead, and an archive Linear refuses is logged and not sent again.
- A file with unsaved edits is skipped, and so is one you edit while the sync runs, whether or not you save it meanwhile: its headings neither pull nor push until the next sync, and the sync neither edits nor saves it. A buffer whose file changed on disk is reverted first if it has no unsaved edits. The sync never deletes heading text.
- A sync that fails, as one does offline, leaves the files it read to be read again by the next sync, so that edits it did not send are sent then. A sync interrupted by =C-g=, or by leaving a debugger opened inside it, ends as failed too, so the next one is not held up behind it. So does one that fails after another package answers it, such as ~org-linear-merge-body-function~ with a model's reply, or one whose failure cannot save what it had linked.
- Several keywords can stand for one Linear state, through ~org-linear-keyword-states~; a heading keeps its keyword while its issue stays in that state. Likewise several cookies can stand for one priority, through ~org-linear-priorities~, and a heading keeps its cookie while its issue keeps that priority. A keyword with no state is sent as the team's first unstarted state, or first completed one for a done keyword; a state whose keyword Org lacks arrives as Org's first open or done keyword.
- Assignees are left alone, except that with ~org-linear-assign-new-issues~ set, each issue the sync creates is assigned to you, the owner of the API key, so that it shows under Linear's "My issues". Issues that already exist keep their assignee.

#+vindex: org-linear-merge-body-function
Linear rewrites the Markdown it is sent in its own style (bare links become =[URL](<URL>)=, =-= bullets become =*=, trailing spaces go), so the sync records the description as Linear stored it, in both layouts; the rewrite is never taken for an edit made in Linear.

A description edited in Linear replaces the heading's body when Linear's stored text of the old description converts back to exactly that body, so that the conversion loses nothing. Otherwise, because of markup Markdown cannot hold, such as a source block's header arguments, ~org-linear-merge-body-function~ merges the two: it gets the Org body, the Markdown of the last sync, Linear's new Markdown and a callback, and calls the callback with the merged Org body, or =nil=. The result is used only if it says what Linear's text says, compared as Org. Otherwise, or when the option is =nil=, the body stays and the log says why; that Linear text is not merged again, but a later edit on either side is. A model makes a good merge function.

#+findex: org-linear-preview
=M-x org-linear-preview= lists, per file, the headings the next sync would create, and the files it would skip, without sending or writing anything, and closes again the files it had to open. Run it before the first sync.

A configuration might look like this:

#+begin_src emacs-lisp
(setq org-linear-profiles
      '((personal :layout in-place
                  :teams ("ME")
                  :directories ("~/notes")
                  :exclude-files ("/checklists\\.org\\'")
                  :exclude-tags ("noexport")
                  :exclude-keywords ("PROJECT")
                  :inbox-file "~/notes/inbox.org"
                  :conflict-winner org
                  :api-key-command ("my-password-tool" "read" "linear-personal"))))
#+end_src

** Projects, initiatives and milestones
:PROPERTIES:
:CUSTOM_ID: h:hierarchy
:END:

#+vindex: org-linear-project-keywords
#+vindex: org-linear-milestone-keywords
By default each TODO heading is an issue of its own, whatever headings it sits under. Set ~org-linear-project-keywords~ to the keywords of your project headings, such as ="PROJECT"=, and ~org-linear-milestone-keywords~ to those of your milestone headings, such as ="MILESTONE"=, and the nesting syncs too. Both are =nil= by default, which leaves the layout as described above. A heading with one of these keywords is never an issue. The keywords must be TODO keywords of your files, and must not be in ~org-linear-exclude-keywords~, which would leave their headings out.

A /task/ here is any heading synced as an issue. The headings map to Linear as follows:

- A task under another task is a sub-issue of the nearest task above it.
- A project heading that holds tasks or milestones becomes a Linear project in the team. It holds them when no other project heading comes between, so a task under a task under it counts.
- A project heading that holds only project headings becomes an initiative. Under another project heading, it becomes a sub-initiative of that heading's initiative.
- A project heading that holds both becomes an initiative, and a Linear project for its own tasks and milestones, since Linear has nothing that is both.
- A project heading that holds nothing becomes a Linear project.
- A Linear project belongs to its own heading's initiative, if it has one, or else to that of the nearest project heading above it.
- A milestone heading becomes a milestone of the Linear project of the nearest project heading above it. Without one, it is not synced, and the log says so.
- An issue belongs to the Linear project of the nearest project heading above it, and to the milestone of the nearest milestone heading between it and that project heading.

For example:

#+begin_example
,* PROJECT Website                 initiative and project
,** TODO Pick a domain             issue in the project Website
,** PROJECT Shop                   project in the initiative Website
,*** MILESTONE Launch              milestone of Shop
,**** TODO Write the copy          issue in Shop, milestone Launch
,***** TODO Draft the headline     sub-issue of Write the copy, in Shop and Launch
#+end_example

Each heading keeps the IDs of its Linear objects in properties, as an issue's heading keeps =LINEAR_UUID=: =LINEAR_PROJECT= for a project, =LINEAR_INITIATIVE= for an initiative and =LINEAR_MILESTONE= for a milestone. A project heading that is both holds both IDs. The sync maintains them; do not edit them.

A heading's title is its object's name, its body the description (a project's or initiative's overview), and its =DEADLINE= the target date. A project heading's keyword gives the status of its project and initiative: an open keyword makes a started project and an active initiative, a done keyword a completed one, and a done keyword sent as a canceled workflow state, by ~org-linear-keyword-states~ or ~org-linear-type-keywords~, a canceled one. A project that Linear moves to another open status, such as planned, keeps its heading's keyword. These fields merge both ways, as an issue's do, with ~org-linear-conflict-winner~ deciding when both sides changed. A milestone's keyword is not synced, since Linear works out a milestone's status itself.

Identity stays with the heading's properties, so moving a heading keeps its objects and changes only its relations, which the next sync sends. Refile a task under another task and it becomes that task's sub-issue; refile a project heading under another one and its project joins that heading's initiative and leaves the one the sync had put it in. The nesting lives in Org: a relation changed in Linear, such as an issue moved there to another project, stays until you move the heading, and the log says so. A project heading keeps the objects it has when what it holds changes, and gets those it now needs.

The safeguards for issues apply to these objects too:

- A new project, initiative or milestone gets its ID as =LINEAR_PENDING_PROJECT=, =LINEAR_PENDING_INITIATIVE= or =LINEAR_PENDING_MILESTONE= before anything is sent, and its file is saved. New objects count toward ~org-linear-create-limit~, and come before the sync's new issues: first initiatives, then projects, then milestones.
- A project or initiative whose heading is no longer in any file is archived in Linear, and a milestone deleted, on the same terms as issues. The vanished issues and objects of a sync count together toward ~org-linear-archive-limit~. Linear's only archive for a project is its trash, from which the project can be restored.
- An object deleted in Linear cancels its heading, which keeps its text and loses the ID, so that the object is not created again.
- A heading that was synced as a task and is now a project or milestone heading, by its keyword or because you turned these options on, has its issue archived and its =LINEAR_UUID= removed, and the log says so; it then gets its project or milestone as a new heading does. These conversions also count toward ~org-linear-archive-limit~: more at once convert none, and those headings keep their issues until there are fewer.

Initiatives must be turned on in Linear, under Settings, Initiatives. While they are off, the sync creates none and logs how many it left out; the projects are created all the same, and join their initiatives once those exist. Sub-initiatives need Linear's Enterprise plan: elsewhere Linear refuses to nest an initiative, and the sync logs the refusal and does not send it again until the heading moves.

=M-x org-linear-preview= also lists the projects, initiatives and milestones the next sync would create.

#+begin_src emacs-lisp
(setq org-linear-profiles
      '((personal :layout in-place
                  :teams ("ME")
                  :directories ("~/notes")
                  :project-keywords ("PROJECT")
                  :milestone-keywords ("MILESTONE")
                  :conflict-winner org)))
#+end_src

Turning the options on makes the next sync read every file again and send the relations of the issues already linked, so expect that sync to be a large one.

* Limits
:PROPERTIES:
:CUSTOM_ID: h:limits
:END:

- Editing or deleting a note that is already in Linear is not sent; only new notes are.
- Comment replies are not shown.
- An issue that re-enters the file, for instance after being reopened, gets its comments again from Linear, but your old notes on it are not restored.
- Markdown headings in a description become bold lines, since an Org heading inside an issue's body would split the issue.
- The sync reads up to 250 labels and 250 projects, and up to 100 comments per issue. A label beyond those 250 shows no tag, but editing the tags never removes it from the issue.
