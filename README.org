This manual describes the features and customization options for the Emacs Lisp file =org-linear.el=.

* Overview
:PROPERTIES:
:CUSTOM_ID: h:overview
:END:

=org-linear.el= keeps the issues of one or more [[https://linear.app][Linear]] teams in an Org file and syncs the two in both directions. You work on your issues with the Org commands you already use: change a TODO keyword to move an issue through its workflow, set a deadline for its due date, add a note to comment on it, refile it to move it to another project. Changes made in Linear, by you or by your colleagues, reach the file at the next sync.

Linear stays the authoritative copy and the file is a mirror. The package exists because the alternatives each give up half of that: Linear's own interface lives outside Emacs, and a one-way export cannot be edited. Unlike an export, =org-linear= remembers what each issue looked like at the last sync, so it can tell which side changed a field and merge the two without overwriting either.

The package talks to Linear's GraphQL API through =curl= and converts descriptions and comments between Markdown and Org with [[https://pandoc.org][pandoc]]. Both run as subprocesses, so Emacs never waits on the network.

Its capabilities fall into four groups:

- The file: how issues, projects and their fields appear in Org ([[#h:the-file][The file]]).
- Syncing: when a sync runs, how it merges, and what happens on conflicts ([[#h:syncing][Syncing]]).
- Setup: the API key, the teams and the mappings ([[#h:user-options][User options]]).
- The agenda: a single command that lists your open issues, and your deadlines among your other tasks ([[#h:agenda][The agenda]]).

* Installation
:PROPERTIES:
:CUSTOM_ID: h:installation
:END:

=org-linear= requires Emacs 29.1 or later, Org 9.7 or later, and the =curl= and =pandoc= programs on your =exec-path=.

With Elpaca:

#+begin_src emacs-lisp
(use-package org-linear
  :ensure (:host github :repo "benthamite/org-linear")
  :custom
  (org-linear-teams '("ENG"))
  :config
  (org-linear-auto-sync-mode))
#+end_src

With Emacs's built-in =package-vc= (Emacs 30 or later):

#+begin_src emacs-lisp
(use-package org-linear
  :vc (:url "https://github.com/benthamite/org-linear")
  :custom
  (org-linear-teams '("ENG"))
  :config
  (org-linear-auto-sync-mode))
#+end_src

Then create a personal API key in Linear (Settings, Security & access, Personal API keys), give it access to the teams you mirror, and make it available to the package ([[#h:api-key][The API key]]).

* The file
:PROPERTIES:
:CUSTOM_ID: h:the-file
:END:

The file is ~org-linear-file~. When it does not exist, the first sync creates it with ~org-linear-file-header~ and fills it. Each project is a level-1 heading with a =LINEAR_PROJECT= property, and each issue a level-2 heading under its project. Issues without a project go under a heading named "No project".

#+begin_src org
,* Website
:PROPERTIES:
:LINEAR_PROJECT: 3f1c...
:END:
,** DOING [#B] Fix the broken signup form                  :ana:bug:
DEADLINE: <2026-11-12 Thu>
:PROPERTIES:
:LINEAR_ID: ENG-123
:LINEAR_UUID: 6b0e...
:LINEAR_URL: https://linear.app/acme/issue/ENG-123/fix-the-broken-signup-form
:END:
:LOGBOOK:
- Note taken on [2026-11-02 Mon 10:14] (Sam Lee) \\
  I can reproduce it on Safari only.
:END:
The form rejects valid email addresses with a plus sign.
#+end_src

** How fields map
:PROPERTIES:
:CUSTOM_ID: h:field-mapping
:END:

| Linear         | Org                                                          |
|----------------+--------------------------------------------------------------|
| Title          | The heading's title                                          |
| Workflow state | TODO keyword ([[#h:states][Workflow states and keywords]])                   |
| Priority       | Priority cookie (~org-linear-priorities~)                    |
| Assignee       | A tag for the person (~org-linear-user-tags~)                |
| Labels         | Tags                                                         |
| Due date       | =DEADLINE=                                                   |
| Project        | The level-1 heading the issue sits under                     |
| Description    | The heading's body, converted from and to Markdown by pandoc |
| Comments       | Notes in the log drawer                                      |

The identifier, the issue's internal ID and its URL are kept in the =LINEAR_ID=, =LINEAR_UUID= and =LINEAR_URL= properties. The sync maintains them; do not edit them.

Tags that name neither a team member nor a label are yours: the sync leaves them alone and never sends them. A label's tag is its name with every character Org does not allow in tags replaced by =_=, so the label =requested-by:peter= becomes the tag =requested_by_peter=.

=SCHEDULED= is not synced, since Linear issues have no start date. Use it freely to defer an issue in your own agenda.

** Workflow states and keywords
:PROPERTIES:
:CUSTOM_ID: h:states
:END:

Each issue's workflow state becomes a TODO keyword. By default the keyword depends only on the state's type (~org-linear-type-keywords~): triage issues are =TRIAGE=, backlog issues =BACKLOG=, unstarted ones =TODO=, started ones =DOING=, completed ones =DONE=, and canceled or duplicate ones =CANCELLED=. ~org-linear-state-keywords~ gives individual states keywords of their own, for instance a =WAITING= keyword for a state named "Waiting".

When you change a keyword in the file, the sync sends it as the state ~org-linear-keyword-states~ names for it, or else as the first state of the issue's team that maps to that keyword, in Linear's order of state types and positions.

The file's own =#+TODO= line, written from ~org-linear-file-header~ when the file is created, must list every keyword these options can produce. The default header marks =CANCELLED= with =@=, so Org asks for a note when you cancel an issue; the sync posts that note as a comment, which records why the issue was dropped.

** Working with issues
:PROPERTIES:
:CUSTOM_ID: h:working-with-issues
:END:

Edit issues with ordinary Org commands, then save the file; with ~org-linear-auto-sync-mode~ the save sends your changes ([[#h:syncing][Syncing]]).

- To comment on an issue, add a note with =C-c C-z= (~org-add-note~). Notes attached to state changes, such as the one the default header asks for when you cancel an issue, are posted too, prefixed with the new keyword.
- To create an issue, add a level-2 heading with a TODO keyword under a project heading, with its description as the body. At the next sync it is created in Linear, in the project's team, and gets its =LINEAR_ID=.
- To move an issue to another project, refile it under that project's heading.
- To assign an issue, tag it with the person's tag; an issue has one assignee, so a heading with two people's tags sends no assignee and the sync log says why.

Deleting a heading does not delete the issue: it comes back at the next sync, with its description and comments. To drop an issue, cancel it.

#+findex: org-linear-browse
=M-x org-linear-browse= opens the issue at point in your browser.

#+findex: org-linear-visit
=M-x org-linear-visit= visits ~org-linear-file~.

** Closed issues
:PROPERTIES:
:CUSTOM_ID: h:closed-issues
:END:

The file holds every open issue of the teams and the issues closed in the last ~org-linear-closed-retention-days~ days. Older closed issues leave the file at the next sync, unless their heading holds something not yet in Linear: unsent edits or notes, or subheadings of your own. Such a heading stays, keeps syncing its edits, and leaves once it has nothing unsent; subheadings keep it for good, and the sync log says so.

* Syncing
:PROPERTIES:
:CUSTOM_ID: h:syncing
:END:

#+findex: org-linear-sync
=M-x org-linear-sync= saves the file, fetches the teams' issues, merges them with the file and sends the file's changes to Linear. It returns at once; the work runs in the background and a message reports what changed. A sync that changes nothing says nothing, so background syncs stay out of your echo area. The first sync converts every description and comment, so it can take a few minutes; later ones convert only what changed.

The merge is three-way. For each field the sync compares the file and Linear with the issue as it was at the last sync, kept in ~org-linear-state-file~:

- A field changed only in Linear is updated in the file.
- A field changed only in the file is sent to Linear.
- When both sides changed a field, Linear's value wins, and yours is recorded in the sync log.

Before each write the sync checks when the issue was last edited. If someone changed it in Linear after the sync read it, the write is refused and the issue is merged again at the next sync, so a change made in Linear is never overwritten. A write Linear rejects, for instance for an invalid value, is logged and not retried until you change what was sent; the sync's other writes still go through.

A sync never changes the file while it has unsaved edits, and never applies changes if the file changed on disk since you visited it. The changes a sync makes clear the buffer's undo history, since undoing them would send a reversal of your colleagues' changes to Linear.

#+findex: org-linear-auto-sync-mode
#+findex: org-linear-file-mode
~org-linear-auto-sync-mode~ is a global minor mode that syncs whenever you save or visit the file, and every ~org-linear-pull-interval~ seconds while the file has no unsaved edits. In the file's buffer it turns on ~org-linear-file-mode~, which runs a sync after each save.

#+findex: org-linear-show-log
=M-x org-linear-show-log= shows the sync log: conflicts, refused and rejected writes, issues not created, and errors. When a sync fails, its message points there.

* The agenda
:PROPERTIES:
:CUSTOM_ID: h:agenda
:END:

#+findex: org-linear-my-issues
#+vindex: org-linear-my-issues-sections
The file holds every open issue of the teams, so it is not the place to see what is yours. =M-x org-linear-my-issues= is: it opens an agenda of your open issues, with each one's project and due month and day, grouped into the sections of ~org-linear-my-issues-sections~. By default those are triage, in progress, waiting and to do; a section whose keyword the file does not define is left out, and backlog issues are not shown. Each call rebuilds the list, even with ~org-agenda-sticky~ on. From the list, =t= changes an issue's status, =RET= jumps to its heading, =s= saves the file, which sends your changes to Linear, and =g= refreshes the list.

Add ~org-linear-file~ to ~org-agenda-files~ to see your issues' deadlines with the rest of your tasks.

#+findex: org-linear-agenda-skip
#+vindex: org-linear-hide-others-in-agenda
#+vindex: org-linear-agenda-keep-tags
~org-linear-agenda-skip~ hides issues assigned to someone else. Set it as ~org-agenda-skip-function-global~ to apply it to every agenda view; issues with no assignee and issues assigned to you stay. So do issues with a tag in ~org-linear-agenda-keep-tags~, =nil= by default, which suits a team that labels work it shares, for instance with =joint=. ~org-linear-hide-others-in-agenda~, =t= by default, turns the filter off without removing it.

#+begin_src emacs-lisp
(setq org-agenda-skip-function-global #'org-linear-agenda-skip)
#+end_src

* Transient menu
:PROPERTIES:
:CUSTOM_ID: h:transient-menu
:END:

#+findex: org-linear-menu
=M-x org-linear-menu= gathers the package's commands in a transient menu. The package binds it to no key, so bind it yourself if you use it often.

| Key | Command                     | What it does                                 |
|-----+-----------------------------+----------------------------------------------|
| =m= | ~org-linear-my-issues~      | Show your open issues                        |
| =v= | ~org-linear-visit~          | Visit the file                               |
| =o= | ~org-linear-browse~         | Open the issue at point in Linear            |
| =s= | ~org-linear-sync~           | Sync now                                     |
| =a= | ~org-linear-auto-sync-mode~ | Turn syncing on save, visit and timer on/off |
| =l= | ~org-linear-show-log~       | Show the sync log                            |

The =o= key appears only when point is on an issue in the file. The =a= key shows whether the mode is on, and the menu stays open after you press it.

* User options
:PROPERTIES:
:CUSTOM_ID: h:user-options
:END:

** Teams and file
:PROPERTIES:
:CUSTOM_ID: h:teams-and-file
:END:

#+vindex: org-linear-teams
The user option ~org-linear-teams~ lists the keys of the teams whose issues the file mirrors, such as ="ENG"=. It is =nil= by default, and a sync refuses to run until you set it.

#+vindex: org-linear-file
~org-linear-file~ is the mirrored Org file, by default =linear.org= in ~org-directory~.

#+vindex: org-linear-file-header
~org-linear-file-header~ is the text a new file starts with. Its =#+TODO= line must cover the keywords of [[#h:states][Workflow states and keywords]], and its =#+PRIORITIES= line the cookies of ~org-linear-priorities~. Notes must go into a drawer, or they would count as part of the description: the default header's =logdrawer= startup option sees to that, and you may drop it if your ~org-log-into-drawer~ is already set. Change the header before the first sync; afterwards, edit the file's header directly.

#+vindex: org-linear-state-file
~org-linear-state-file~ holds each issue as it was at the last sync, by default =org-linear/state.eld= under =$XDG_STATE_HOME= or =~/.local/state=. Deleting it makes the next sync treat Linear's values as the starting point.

#+vindex: org-linear-closed-retention-days
~org-linear-closed-retention-days~, 7 by default, is how many days a closed issue stays in the file.

#+vindex: org-linear-pull-interval
~org-linear-pull-interval~, 600 by default, is the number of seconds between background syncs in ~org-linear-auto-sync-mode~.

** The API key
:PROPERTIES:
:CUSTOM_ID: h:api-key
:END:

The sync reads your Linear API key at the start of each sync and forgets it at the end.

#+vindex: org-linear-api-key-command
~org-linear-api-key-command~, a command as a list of strings, prints the key. It runs asynchronously, so it suits a password manager's command line. It takes precedence over the next option.

#+vindex: org-linear-api-key
~org-linear-api-key~ is the key itself or a function that returns it. When it is =nil=, the default, the key is read with =auth-source= for the host =api.linear.app=, for instance from a line in =~/.authinfo.gpg=:

#+begin_example
machine api.linear.app password lin_api_YOURKEY
#+end_example

#+vindex: org-linear-api-key-forget-command
If your command caches the key, set ~org-linear-api-key-forget-command~ to a command that drops the cached copy. When Linear rejects the key, the sync runs it and retries once, so a rotated key is read afresh.

The key reaches =curl= on its standard input, never on its command line, where other processes could see it.

** Mappings
:PROPERTIES:
:CUSTOM_ID: h:mapping-options
:END:

#+vindex: org-linear-type-keywords
#+vindex: org-linear-state-keywords
#+vindex: org-linear-keyword-states
~org-linear-type-keywords~ maps state types to keywords, ~org-linear-state-keywords~ maps individual state names to keywords, and ~org-linear-keyword-states~ chooses which state a keyword is sent as ([[#h:states][Workflow states and keywords]]). For example, a team with a "Waiting" state and a "Rejected" state might use:

#+begin_src emacs-lisp
(setq org-linear-state-keywords '(("Waiting" . "WAITING"))
      org-linear-keyword-states '(("CANCELLED" . "Rejected")))
#+end_src

#+vindex: org-linear-priorities
~org-linear-priorities~ maps Linear's priorities, 1 (urgent) to 4 (low), to Org cookies; it is =A= to =D= by default. Linear's "no priority" is no cookie. A cookie not listed is sent as the priority of the nearest listed cookie above it, so with numeric priorities you can map only some numbers:

#+begin_src emacs-lisp
(setq org-linear-priorities '((1 . "1") (2 . "2") (3 . "4") (4 . "6")))
#+end_src

#+vindex: org-linear-user-tags
~org-linear-user-tags~ maps team members' names to tags. A member not listed gets the first word of their name in lower case. Members of other teams have no tag; an issue assigned to one of them keeps that assignee, since the file cannot represent it.

** Programs
:PROPERTIES:
:CUSTOM_ID: h:programs
:END:

#+vindex: org-linear-curl-program
#+vindex: org-linear-pandoc-program
#+vindex: org-linear-timeout
~org-linear-curl-program~ and ~org-linear-pandoc-program~ name the =curl= and =pandoc= executables. ~org-linear-timeout~, 60 by default, is how many seconds a request to Linear may take before it is abandoned and the sync fails.

* Limits
:PROPERTIES:
:CUSTOM_ID: h:limits
:END:

- Editing or deleting a note that is already in Linear is not sent; only new notes are.
- Comment replies are not shown.
- An issue that re-enters the file, for instance after being reopened, gets its comments again from Linear, but your old notes on it are not restored.
- Markdown headings in a description become bold lines, since an Org heading inside an issue's body would split the issue.
- The sync reads up to 250 labels and 250 projects, and up to 100 comments per issue.
